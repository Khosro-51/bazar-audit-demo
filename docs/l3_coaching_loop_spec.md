# L3 — Progress / Coaching Loop — Specification (design only)

**Date:** 2026-06-15 · **Status:** spec for approval, *before any code*.
**Authority:** implements the locked agreement in `BAZAR_L2_L3_AGENT_DESIGN.md` §3 (L3) and §8 ("Line 4 — Progress Loop", locked rule #4: three-state verdict with uncertainty). Where this spec and that agreement disagree, the agreement wins.
**Scope:** **L3-core only** — the **deterministic out-of-sample comparison engine** (Line 4). **No LLM. No Agent. No live market behavior. No L1/L2 engine changes.** The conversational mentor (Line 3 Agent) sits *on top of* L3-core later and is out of scope here.

This spec is the L3 analog of the L2 "قفل‌نامه"; implementation (an "L3 Prompt 7") is gated on approval of this spec, a live Supabase backend, and ideally real L1/L2 cycle data.

## 1. Product definition

L3 closes the loop. The user took an **L2 Playbook (Candidate v1)**, traded **30+ new trades** under it, and uploads them. L3-core deterministically asks, **out-of-sample**:

1. **Did the user actually follow each rule?** (adherence — you cannot judge an untested change)
2. **For the rules they followed, did the targeted behavior measurably change** vs the baseline — **with an honest uncertainty band**?
3. **What's the verdict** — `improved` / `worsened` / `insufficient_evidence` (the locked three-state)?
4. **What's new or resolved** this cycle, and **what should Playbook v2 be**?

This is the product's real differentiator: a closed **hypothesis → out-of-sample test → re-tune** loop on a bullet-proof statistical core. The honest coach often says *"not yet judgeable"* — and means it.

## 2. Non-goals (hard)

- **Not** a verdict machine that declares "you improved" on one noisy 30-trade cycle. Single cycles are usually `insufficient_evidence`; firm verdicts accrue across cycles.
- **No** LLM in L3-core; **no** narration (that's the Line-3 Agent). **No** signals/buy/sell/price/SL/TP. **No** profit claims.
- **No** invented numbers — every figure is computed by the deterministic engine (golden rule).
- **No** in-sample self-grading: the cycle is judged on its **own** out-of-sample data; the baseline is treated as the (optimistic, selection-biased) starting point, with regression-to-the-mean acknowledged.

## 3. Inputs

- **Playbook v1** — `bazar_playbook.Playbook.to_dict()` being tested: its `rules[]` (op/target/value/source/evidence) and `next_cycle.success_metrics` (the pre-declared metrics to move).
- **Baseline audit** — the L1 `AuditReport.to_dict()` the playbook was built from (core_metrics + insight snapshots, incl. per-segment breakdowns).
- **New-cycle trades** — a fresh DataFrame of the next 30+ trades (same required columns as L1).
- **Cycle history** (optional) — prior `CycleReport`s for this user (from Supabase), for multi-cycle pooling.

Privacy: L3-core operates on metrics/snapshots + the new df locally; only **aggregates + snapshots + the JSON artifacts** are persisted (never raw trade rows leave the trusted layer). The user is keyed by `email_hash` (reusing E1's hashing), never raw email.

## 4. Outputs

1. **CycleReport** (JSON, §9) — per-rule adherence + metric delta (with CI) + verdict; overall three-state verdict; new/resolved findings; multi-cycle pooling.
2. **Playbook v2** — regenerated by **calling L2** (`generate_playbook`) on the new (or cumulative) audit, with each carried-over rule annotated by its L3 verdict; rules may be **graduated** or **retired** only under the gating in §7.
3. A deterministic **"Cycle Review"** preview (multilingual templating, no LLM), feature-flagged like L2.

## 5. The comparison & verdict logic (deterministic, statistically honest)

For the new cycle, L3-core first runs the **L1 audit on the new trades** (out-of-sample) → `current` metrics + insights. Then, per playbook rule with a measurable target:

**Step A — adherence (§6).** Did behavior change as prescribed? If not followed → verdict `insufficient_evidence`, `reason="not_followed"` (never `worsened` — you can't fail an untested change).

**Step B — metric delta with CI.** Compare the rule's target metric, baseline → current, using the appropriate test on the **new** data:
- win-rate-type (overall WR, session/symbol WR, post-loss WR): **two-proportion z** on decided trades (reusing the engine's `_two_prop_p_less` discipline) + a CI on the difference.
- expectancy ($ or R): **difference-in-means** with a CI (Welch) using the new per-trade values.
- count/cooldown (trade_count, cooldown): adherence *is* the metric (deterministic), plus the downstream WR/expectancy effect.

**Step C — verdict (three-state):**
- `improved` — the CI on the delta excludes zero in the favorable direction **and** the cycle has enough decided trades. *Single cycle → reported as "improving (early)"; a firm "improved" requires the multi-cycle pooled CI (§7).*
- `worsened` — CI excludes zero in the adverse direction (symmetric).
- `insufficient_evidence` — otherwise (the default), with a `reason` (`wide_ci` / `too_few_trades` / `not_followed` / `unverifiable`).

**Overall cycle verdict** = a conservative roll-up: `worsened` if any followed firm rule worsened with evidence; else `improved` only if ≥1 followed rule improved with evidence and none worsened; else `insufficient_evidence`. Multiple-comparison caution: when many rules are evaluated, the same union-FP discipline as L1 applies — prefer `insufficient_evidence` over a borderline `improved`.

**Regression-to-the-mean guard.** The baseline segment metrics are in-sample (the playbook was *fit* to them), so some "improvement" is expected by regression alone. L3-core flags this: a rule is only `improved` if the out-of-sample cycle beats baseline by more than a regression allowance, or (better) if it beats the **counterfactual expectation** the playbook declared. Documented as a first-class caveat in every CycleReport.

## 6. Adherence (the L3-core differentiator)

Computed deterministically from the new df, per rule `op`/`target`:

| rule | adherence check | "followed" if |
|------|-----------------|---------------|
| `limit trade_count=N` | observed max trades/day | ≥80% of days ≤ N |
| `limit`/`remove session=X` | share of trades in X (new vs baseline) | share dropped materially (e.g. ≥50% reduction or →0 for remove) |
| `limit`/`paper_trade symbol=Y` | share of trades in Y | dropped materially (paper_trade: Y absent from the live upload) |
| `limit cooldown=60` | post-loss fast-reentry count (via `_post_loss_indices`) | fast reentries dropped materially |
| `limit risk=fixed_pct` | dispersion of size vs account state (drawdown buckets) | size no longer scales with drawdown |
| `paper_trade strategy_core` | unverifiable from a live upload | → `unverifiable` (verdict insufficient_evidence) |
| `track`/`test` | did the tracked column now appear / enough data to judge? | n/a (these are data-collection, evaluated as "now judgeable?") |

Adherence yields `{followed: bool|null, observed, prescribed, adherence_pct, note}`. **A low-adherence rule is never graded `worsened`.** This single mechanism is what makes the loop honest — most "it didn't work" claims in the wild are really "they didn't do it."

## 7. Multi-cycle pooling & rule graduation (gated)

- **Pooling:** each cycle stores the rule's per-cycle `(wins, decided)` / `(sum, n)` for its target metric. Across cycles, L3-core pools (e.g. summed contingency / inverse-variance) so power accrues. A **firm** `improved`/`worsened` verdict requires the **pooled** CI to exclude zero — never a single 30-trade cycle.
- **Graduation (escalate a rule):** only after ≥ *K* cumulative cycles of followed-and-improved-with-pooled-evidence may a rule escalate — e.g. `paper_trade` → live, or `limit` → `remove`. *K* and the exact gate are §11 decisions; default conservative (≥2 cycles, pooled CI excludes zero).
- **Retirement (drop a rule):** a rule that is followed but pooled-`worsened` (or never helps after several cycles) is retired with a note. A rule that's never followed is *not* retired — it's re-surfaced as "still untested."
- **New issues:** findings that appear out-of-sample (not in baseline) are added to Playbook v2 as fresh hypotheses (via L2's normal mapping).

## 8. Statistical methods (summary, no scipy)

- Two-proportion z + Wald CI on the difference for win-rate metrics (consistent with `_two_prop_p_less`).
- Welch difference-in-means + normal CI for expectancy.
- Permutation reuse where an L1 insight already provides a p-value (segment toxicity / cliff) — L3 re-runs the L1 gate on the new cycle and compares finding presence/strength.
- Pooling: inverse-variance for means; summed wins/decided for proportions.
- All CIs reported; verdict keyed off whether the CI excludes zero **and** the regression allowance.

## 10. Persistence & privacy (Supabase)

- New table `cycles` (per-user history), keyed by `email_hash`; stores the CycleReport JSON + the pooled aggregates needed for §7. **No raw trade rows.** Reuses the E1 `StateStore` backend selection / fail-closed posture; a migration `db/migrations/0002_cycles.sql` accompanies implementation.
- Per-user "memory" = this cycle history; it is what the Line-3 Agent will later narrate over (RAG on the user's own aggregates — never general knowledge, never raw rows).
- Retention/erasure policy is a §11 decision (the entitlement model already hashes email; cycles inherit it).

## 11. Safety guardrails

- Same **Forbidden Output Policy** as L2 (no signal/buy/sell/price/SL/TP, no profit promises, no invented numbers, no firm verdict on insufficient data).
- The canonical honest output is **`insufficient_evidence` / "not yet judgeable"**; L3-core must be *comfortable* saying it (locked rule #4). A single cycle defaults to it.
- Deterministic: no clocks/RNG in the pure engine (`generated_at` caller-stamped); permutations seeded from data like L1.
- All numbers engine-computed; verdicts gated by CIs + adherence + (for firm verdicts) multi-cycle pooling.

## 12. Test plan (write tests before implementation)

1. **Determinism** — same (playbook, baseline, new df, history) → identical CycleReport.
2. **Adherence gating** — a rule the user ignored → `insufficient_evidence/not_followed`, **never** `worsened`.
3. **No-change cycle honesty (L3 Monte-Carlo analog)** — feed a new cycle drawn from the *same* zero-edge distribution as baseline; the cycle verdict must be `insufficient_evidence` (no false `improved`/`worsened`) at the L1 false-finding ceiling.
4. **Genuine improvement** — a constructed cycle where the followed rule's metric clearly moves with tight CI across **two** pooled cycles → `improved` (and only then "firm").
5. **Single-cycle restraint** — the same improvement in one cycle → "improving (early)", not a firm `improved`/graduation.
6. **Regression guard** — an in-sample-optimistic baseline + a mean-reverting cycle does not yield a false `improved`.
7. **Graduation gate** — `paper_trade`→live / `limit`→`remove` only after the pooled gate; never single-cycle.
8. **Three-state only** — verdicts are always one of the three; schema validates.
9. **Forbidden language** — rendered Cycle Review (en/fa/ar) passes the safety scan.
10. **Privacy** — persisted record contains only `email_hash` + aggregates/JSON, no raw trade fields.
11. **Number provenance** — every metric in a rule_evaluation traces to the engine (baseline snapshot or a recomputed value on the new df).

## 14. Key design choices
- **Out-of-sample is the whole point** — the cycle is judged on its own new data, not by refitting; this is the anti-overfitting moat.
- **Adherence before verdict** — never grade an untested change; most "it didn't work" is "they didn't do it."
- **Three-state + uncertainty, firm verdicts only when pooled** — the honest coach says "not yet judgeable" by default.
- **Engine is the brain; L3 compiles comparisons** — same golden rule as L1/L2; the Agent (later) only narrates tool-results.
- **Privacy-first persistence** — `email_hash` + aggregates only; the user's own history is the memory, never general knowledge or raw rows.
